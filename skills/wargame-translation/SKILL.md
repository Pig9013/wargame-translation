# 兵棋规则逐字翻译 (Wargame Rulebook Literal Translation)

## 概述

这是一个为兵棋推演（Board Wargame）规则书设计的精确翻译工作流。用户的目的是**中英文对照查规则**，因此翻译标准是**字面对应优先于文学优美**——逐字逐句对应原文，专业名词统一且可回溯，标题编号分毫不差。

**核心原则**：可查规则 > 信达雅。让读者可以拿着中文译文反向定位英文原文的每一个句子。

### 2026-10-21 标准流程：两步交付

1. **内容源**：本 skill 产出 `<作品>_zh-CN.md`（或项目既定命名的 `.md`），是唯一内容源。
2. **排版版**：内容定稿后，用 skill `wargame-rulebook-layout`（GBII Ds 版方案）排成 PDF，并按对应位置嵌入原书插图。排版阶段**不改正文一字**。

**权威顺序**（务必分清两个层面）：

| 层面 | 权威 |
|:--|:--|
| 规则**含义** | 英文原书（最终权威；已有中译只能帮助理解，不能覆盖原文） |
| **术语选择** | 该系列指定的中文基准（见第二步；SCS 为通规中文 → CTO → 自拟） |
| 原书自身错误 | 照录原编号/原文，另设「原书勘误注记」，不擅改 |

## 第零步：前置确认

开始翻译前必须确认：

1. **系列类型**：SCS / TCS / GTS / OCS / VUCA / BCS / GBACW / LOB / 其他独立作品；**18xx 走 `18xx-translation`**，不套用本 skill（2026-10-25 起从 `18xx-analysis` 拆出）。
2. **英文原书**：确认版本、印次、页数；若有 OCR/文本层问题，先做第一步的抽取核对。
3. **已有中文规则**：该系列的通规中译、专规中译、术语表；记录文件名与版本。
4. **工作目录**：确认项目文件夹；中间文件统一放 `_translation_work/`。
5. **交付物**：`.md` 内容源 + 排版版 PDF（默认 GBII Ds 版）；是否要可信度评估、是否要插图清单，按项目确认。
6. **版本与标签**：内容版号（如 v1.0）、排版标签（如 Ds版）、日期；每次改动升版本并写沿革。
7. **用户审核点**：术语库、原书勘误、可疑段落、插图清单——能先给用户看的先看，避免后期大范围返工。

## 第一步：原文抽取与版本核对

### 1.1 文本抽取（双栏书的关键）

1. 优先用 PyMuPDF 逐页抽取；**不要**用 `pdftotext -layout` 直接处理双栏规则书——它会左右栏串行，读起来是乱的。
2. 双栏正确读法：`page.get_text('blocks')` 取块 → 按块中心 x 判断左/右栏 → 栏内按 y 排序 → 左栏读完再读右栏。
3. **排除跨栏块**：宽 > 页宽 62% 的块（标题、页眉、通栏表、整页图）单独处理，不参与左右栏排序。
4. **装饰性页码可能是矢量字形而非文本**：`words` 取不到；需渲染成图人工读，或与文档文字层交叉验证。小字号印章式页码必须高倍渲染核对（ToV 曾把 `LXXIX` 误读为 `LXXVI`）。
5. 扫描无文本层的书：本机无 tesseract，不能假装 OCR 成功；要么用现有 OCR 稿并标注“OCR 稿、需核字”，要么逐页目检 + 人工录入。
6. 建立**页码映射**：原书页 → md 章节/锚点；后续插图普查和排版核验都靠它。

### 1.2 原书勘误登记（交付必备）

原书自身经常有错。翻译的职责是**照译 + 留底**，不是替作者改书。

必须逐项检查并记入 md 末尾「## 原书勘误注记」：

- 目录页码错误（整本偏移、个别条目偏移）。
- 正文排印笔误（拼写、重复词、标点、大小写）。
- 交叉引用错误（引用的节号不存在或指错节）。
- 规则与示例互相矛盾（最危险；两处都照译，在勘误注记里明确标出，提醒上桌前与对手约定）。
- 编号跳跃/重复（如原书出现两个 3.1d、缺 2.5e/2.5f）。
- 图表与正文不一致（TEC/CRT/示例）。

写法：**正文保留原编号与原义，不改动**；勘误注记逐条写「原书位置 → 原文 → 问题 → 译文处理」。VUCA《胜利之痕》的 22 处勘误（11 处目录页码、9 处笔误、1 处交叉引用、1 处规则/示例矛盾）是标准样板。

### 1.3 版本核对

- 确认翻译所依据的英文版次（如 GBII 2011 Reprint、SCS Rules v18、TCS v4.02）。
- 若同一作品有多个版次，在翻译说明里写明“本译依据哪一版”；不要把不同版次的规则混译。
- 已有中译若依据旧版，术语可参考，但内容以本次英文原书为准。

## 第二步：建立专业名词对照库（最重要的一步，不可跳过）

这是整个翻译工作的基础，也是质量的关键。必须在开始正文翻译之前完成。

1. **定位基准文件**：
   - 全项目术语库总表：`D:\兵棋\术语库\兵棋术语总表.md`（跨系列对照 + 版本差异）；索引：`D:\兵棋\术语库索引.md`。先查这里，再决定沿用还是新建。
   - 英文通规：如 `TCS_v402v7_Rules.pdf`、`SCS_Rules_v18_September_2015.pdf`。
   - 已有中文规则：如 `TCS4.0中规.pdf`、`SCS 标准战斗系列 系列规则 中文修订版 v1.pdf`。
   - 该系列已有的术语库/对照表（GTS、SCS、VUCA 有独立库；OCS、TCS 的库嵌在译稿附录）。

2. **逐条提取术语**，按以下分类建立对照表：
   - **游戏概念**：Turn（回合）、Phase（阶段）、Impulse（脉冲）、Activation（激活）等
   - **单位类型**：Battalion（营）、Company（连）、Platoon（排）、HQ（指挥部）等
   - **战斗术语**：Barrage（射击）、Close Combat（近战）、Overrun（突袭）、Retreat（撤退）等
   - **地形术语**：Woods（林地）、Rough（崎岖地）、Swamp（沼泽）、Ridge（山脊）等
   - **状态标记**：Fired（已射击）、Moved（已移动）、Disrupted（混乱）、Suppressed（压制）等
   - **游戏系统特有术语**：各系列独有的概念

3. **交叉验证**：
   - 将英文通规术语与已有中文规则中的翻译对应。
   - **术语选择**以该系列指定的中文基准为准（见下表）；基准没有的，参考该系列翻译惯例自拟并标记。
   - **规则含义**仍以英文原文为准；若中文基准的译法会误导含义，在术语表加注说明，而不是悄悄改含义。

4. **分系列术语基准（2026-10 盘点）**：

   | 系列 | 术语基准（优先级从高到低） | 备注 |
   |:--|:--|:--|
   | **SCS** | ①《SCS 标准战斗系列 系列规则 中文修订版 v1》（通规中文，慕容笛译本，词汇表在 PDF 末页）② CTO／觅渡Midu 译本 `D:\兵棋\SCS大全\SCS NA_Rules-CN（剧本未翻译）.pdf` ③ 自拟并记入术语库 | 用户 2026-10-03 裁定，强制适用 |
   | **TCS** | ① `TCS4.0中规.pdf` ② 已有 TCS 专规中译 ③ 自拟 | 不与 SCS 混用 |
   | **GTS** | ① GTS 通规/专规既有术语库 ② 已有中译 ③ 自拟 | 注意 GTS 的 “SCS” 是 Strike-Counter Strike，不是 Standard Combat Series |
   | **OCS** | ① OCS 4.3 中译 ② OCS 2.0i 中译 ③ 朝鲜战争/第三个冬天等专规中译 ④ 自拟 | GBII 重印版即按此链 |
   | **VUCA** | ① GTS/SCS 术语库中通用词 ② ToV 用户裁定表 ③ 自拟 | ToV 与 Traces of War 同架构，可互参；ToH 不同体系 |
   | **美工哥（GMT）** | `D:\兵棋\术语库\美工哥_Terminology_DB.md`（Stalingrad '42 / France '40 / Holland '44 / Salerno '43） | 核心术语抽取，非逐页全量 |
   | **激斗系列** | `D:\兵棋\术语库\激斗_Terminology_DB.md`（A Victory Lost / Traces of War） | 核心术语抽取，非逐页全量 |
   | **18xx** | 英文原书最终权威；已有中译仅参考 | 走 `18xx-translation`，不套用兵棋术语优先级 |

5. **SCS 系列术语裁决（用户 2026-10-03 裁定，强制）**：
   - **SCS 系列的术语一律以《SCS 标准战斗系列 系列规则 中文修订版 v1》（“通规中文”，慕容笛译本）为准**；通规中文没有的术语，取 **CTO 译本**（`D:\兵棋\SCS大全\SCS NA_Rules-CN（剧本未翻译）.pdf`，翻译：CTO／校对：觅渡Midu）的译法；两者皆无，才自行裁定并记入术语库。
   - 通规中文词汇表＝原书末页「附录：中英词汇对照表」。
   - 已裁定对照（首批，随裁定增补）：Overrun＝**突袭**｜Exploitation＝**进击**（Exploitation-capable＝具有可进击能力的）｜Barrage＝**射击**｜Sequence of Play＝**游戏流程**｜Out of Supply＝**断补**（In supply＝有补给）｜Leader＝**将领**（CTO）｜Rebuild Cup＝**重建区**、Tripoli Cup＝**的黎波里区域**（CTO）｜Engineer＝**工兵**、Pioneer＝**战斗工兵**（CTO）。
   - 修改既有译文时逐处核对上下文、勿波及多义词：Assault＝突击、突击炮、突击工兵、突击队；“扩张领土”等普通行文；“炮击海岸”等非 Barrage 语义。
   - 仅适用于 SCS 系列；TCS 等其他系列按各自已有的中文规则为基准。

6. **对照库格式**：

   ```markdown

   | 英文 | 中文 | 首次出现位置 | 依据 |

   ```

7. **提交用户审核**（如可能）：将对照库先发给用户确认，避免后期大范围修改。

## 第三步：逐字逐句翻译

**⚠️ 强制署名**：翻译文件头部必须包含署名行 `**翻译人：** Pig9013 Deepseek大模型`，格式与已有翻译（如 GTS_SCS_Exclusive_Rules_中译）保持一致。此项在质量自查清单中单独检查。

1. **保持原文结构**：
   - 标题编号**完全一致**（如 3.1a、3.2f、5.3c）
   - 段落结构与原文一一对应
   - 列表/编号列表的层级结构与原文一致
   - **不要**合并、拆分或重组原文段落

2. **翻译标准**：
   - **逐字逐句**：每个英文句子对应一个中文句子
   - **不缩写**：原文有的内容全部翻译，不省略任何一句
   - **不扩写**：不添加原文没有的解释、补充或修饰
   - **不杜撰**：不确定的术语严格查对照库，不在对照库中的先标记后统一处理
   - **保留原文逻辑**：不为了中文流畅而调整原文的因果/条件逻辑

3. **特殊元素处理**：
   - **规则编号**：保持原样，如 `[3.1a]`、`(5.2c)`
   - **骰子符号**：保持原文格式，如 `1d6`、`2d10`
   - **表格**：逐格翻译，保持行列结构
   - **图表**：如果原 PDF 中有流程图/示意图，用 markdown 尽可能重现结构；**图片/图框的普查与嵌入见第六步（强制，零遗漏）**
   - **强调/大写**：英文全大写的术语在中文中用**加粗**标示
   - **示例/注释**：原文中的设计注释（Design Note）、示例（Example）必须翻译且保持与正文字体的区分
   - **原书错误**：照译，另记入「原书勘误注记」；不要替作者改编号或改数字

4. **翻译时的工作方法**：
   - 先小段翻译（如 2–3 页原文），确认识别准确
   - 对照规则编号逐条检查：没有漏掉规则编号
   - 翻译完一章后，对照原文检查编号连续性

5. **版本沿革**：在「翻译说明」里保留一行版本沿革；每次改稿都升版本号并写清改了什么（见第七步交付纪律）。

## 第四步：逐段对照检查与可信度评估

### 4.1 逐段对照检查

每翻译完一个章节，进行自我检查：

1. **编号检查**：逐条核对所有规则编号（如 3.1a → 3.1b → 3.1c...），确保没有跳号或遗漏。
2. **内容对照**：拿英文原文，逐句对照翻译，确认：
   - 每个句子都翻译了
   - 没有自行添加的解释
   - 专业术语使用的都是对照库中的译法
3. **逻辑验证**：读一遍中文翻译，确认规则的逻辑关系（if-then、先后顺序、条件触发）与原文一致。
4. **表格/图表验证**：逐格对照；CRT/TEC/TEM 的数值、列序、星号脚注不能错位。

### 4.2 可信度评估（交付必备）

每本译稿末尾附「翻译可信度评估」，按四维打分：

| 维度 | 权重 | 检查点 |
|:--|:--|:--|
| **完整性** | 25% | 每一节、每一段、每一句是否都译了；有无缩写、跳段、漏表 |
| **准确性** | 40% | 是否忠实传达原意；逐字/直译标准；有无自行解释或弱化条件 |
| **术语一致性** | 20% | 同一英文词是否全篇同一译法；是否符合系列术语基准 |
| **结构保真** | 15% | 标题编号、列表层级、表格行列、交叉引用是否与原文对应 |

输出格式：

```markdown
## 翻译可信度评估

**总体可信度：XX%**

| 维度 | 得分 | 说明 |
|:--|:--|:--|
| 完整性 | XX/100 | …… |
| 准确性 | XX/100 | …… |
| 术语一致性 | XX/100 | …… |
| 结构保真 | XX/100 | …… |

### 主要扣分点
1. ……
2. ……

### 术语专项
| 英文 | 中文 | 评价 |
|:--|:--|:--|
| …… | …… | …… |
```

- 目标：**≥90%** 方可交付；低于 90% 先返工再评估。
- 评估要具体到节号和例子，不要只写“总体良好”。
- GTS 两份译稿（通规 92%、专规 90%）是标准样板；专规评估中发现 “Volks Artillerie Korps” 应为“国民炮兵军”而非“人民炮兵军”，这类术语问题要单列。

## 第六步：插图普查与嵌图（强制，零遗漏）

> ⚠️ **易漏点（多次实际踩坑）**：原书中的「Unit Symbol Key（算子示意图框）」「Unit Symbols and Markers」、示意图、地形图标列、照片、地图插图、封底美术等，**很多是用矢量轮廓文字绘制的**——用 `get_text()` 搜索关键词（如搜 “Symbol”）**完全搜不到**，仅凭文本层就下结论“原书没有这些图”会漏图，而用户对此零容忍。

1. **原版全页目检（每本书开工时必做，不得跳过）**：
   - 把英文原版每一页渲染为图片（约 1.4–1.6 倍）**逐页过目**（可用联系表批量看），专门找：图框（symbol key / markers）、示意/示例图、照片、地图插图、图表页（TEC/CRT/TEM）、封底。
   - 同时用程序辅助清单：`page.get_image_info()`（位图照片）+ `page.get_drawings()`（宽 > 95pt、高 > 60pt 的矢量框）。
   - **禁止**仅凭文本搜索（含搜 “Unit Symbol Key” 等）推断“书中没有此图”。

2. **编制插图清单（manifest）**：每本书一份，逐项记录：
   `原书页码/坐标 → 元素名（如 Unit Symbol Key）→ md 锚点（章节/图注句）→ 排版版核验（✔/页码）`。

3. **嵌入规则（两步交付的第二步）**：
   - 图框/示意图/照片/地图/封底美术：从原版 PDF **按坐标区域高分渲染后裁剪**嵌入排版版对应位置（图注句上方钩挂）。图内英文标签属于原图组成部分，**保留不动**。
   - 原书图框中的**文字内容**（symbol 列表、图例、规则表）另在 md 对应位置**誊录为中文**（英文对照），确保 md 单独可读。
   - 复杂数据图表（CRT/TEC/TEM/打击表等）：**逐格誊录为中文表格**写入 md；是否另嵌原图由版式决定。

4. **交付前终检（强制最后一步）**：
   - 对照插图清单**逐条核验**：在排版版 PDF 中渲染对应页，确认该图已插入且位置正确；md 中确认对应誊录/图注存在。
   - 核验结果记入交付说明（如「插图 N/N 已核验」）；**有任一项未核验即不得交付**。
   - 书籍原书确无某类图的（如 SCS IC 原书无独立 symbol key 页——其算子图框在 2.0 页首），在交付说明/附录注明依据。

## 第八步：交付与发布（GitHub，2026-10-25 起）

**每个翻译工作线一个独立仓库，不复用 `WITE2_CN`**。装配与发布按下面执行。

### 8.1 仓库结构

```
README.md              版本 / 目录 / 作品表（系列、页数、版本、日期）/ 版权 / 致谢
CHANGELOG.md           按版本倒序，与 skill / PDF 的版本号对齐
skills/wargame-translation/SKILL.md
skills/wargame-rulebook-layout/     SKILL.md + assets/ + references/
works/<系列>/<作品>/     <作品>_...md（内容源）+ （排版版）.pdf
glossary/              兵棋术语总表.md / 索引 / 各系列 Terminology_DB
```

### 8.2 发布纪律（硬）

- **只发最新版**：同一作品多版本并存时，仓库只留最新一版；旧版本地归档。
- **版本四处一致**：md 版本沿革、PDF 封面/页脚/**元数据**、git tag、Release 标题。已踩过：Railways 排版版封面/页脚 v1.1，PDF 元数据还写着 v1.0——**构建脚本里的版本常量必须随手改**。
- **只发译文与排版件**：不发英文原书 PDF、扫描件、游戏本体、VASSAL 模块。
- **版权声明**（README 必备）：原文版权归原作者/出版社；译文与排版为 Pig9013 的劳动成果；仅供学习交流、禁止商用；权利人可联系删除。
- `.gitattributes` 写 `* -text`（禁止 Git 换行转换改字节；WITE2_CN 曾因 LF 转换导致整批 checksum 失败）。
- 单文件 <100 MB；单仓库建议 <1 GB。
- **Release 说明四段**：① 这版译了什么；② 与上版的差异（勘误/补页/插图）；③ 如何核对（页数、标题数、保真比、插图 N/N）；④ 版权与致谢。

### 8.3 发布前静态自检

运行仓库里的 `tools/verify_repo.py`（每个仓库一份），至少检查：

- [ ] README 里每个作品路径都存在，md 与 PDF 成对；
- [ ] 每个 PDF 的页数/标题/版本与 README 表一致；
- [ ] 没有 >100 MB 文件，没有英文原书/扫描件混入；
- [ ] git tag 与 README/CHANGELOG 版本一致；
- [ ] 术语表/勘误/插图清单齐全（按本 skill 第二、四、六步）。

> 发布不是"传上去就完了"：README 是给陌生人看的入口，必须让他 30 秒内知道"这是什么、有哪些作品、怎么用、版权如何"。

## 常见错误避免（你的用户对这些错误零容忍）

| ❌ 错误做法 | ✅ 正确做法 | 用户反馈 |
|:-----------|:----------|:--------|
| 缩写原文内容，“概括大意” | 原文每一句都翻译，不省略 | “频繁出现缩写” |
| 用近义词代替专业术语 | 严格使用对照库中的固定译法 | “赋予反击机会翻译成允许敌方对你所做之事” |
| 追求中文优美而调整句式 | 保持原文句式，即使中文读起来略生硬 | “这种小聪明有什么意义呢？完全失真” |
| 自己发明标题或编号 | 标题编号与原文完全一致 | “标题（如3.1a 3.2f）不能有丝毫错误” |
| 凭记忆翻译术语，不建对照库 | 先建对照库，翻译时查阅对照库 | “专业名词务必准确且可对应” |
| 两个系列的术语混用 | TCS 是 TCS，SCS 是 SCS，各自独立 | “不能混淆...不同专规彼此独立” |
| SCS 术语自行选用、不先查通规中文 | SCS 术语优先级：通规中文词汇表 → CTO 译本 → 自拟（见第二步第 5 条） | 用户裁定（2026-10-03）：“scs翻译统一采用通规中文的翻译方式” |
| 漏嵌原书插图/图框（如 Unit Symbol Key） | 每本书做原版全页目检 + 插图清单，交付前逐条核验（第六步） | “怎么又漏了……unit symbol key的图”（2026-10-03 两次踩坑） |
| 双栏书用 `pdftotext -layout` 硬抽 | PyMuPDF `get_text('blocks')` 分栏排序（第一步） | 左右栏串行，读起来是乱的 |
| 原书有错就顺手改掉 | 照译 + 「原书勘误注记」留底 | 否则无法与英文原书逐条对照 |
| 只写“翻译完成”，不写可信度 | 四维评估 + 具体扣分点（第四步） | 用户要判断这份译稿能不能拿去查规 |
| 排版时顺手改正文 | md 是唯一内容源，排版不改一字 | 版本对不上、无法回溯 |
| 交付物不升版本号 | 每次改动升版本并写沿革 | 用户靠版本号判断是否最新 |
| PDF 版本与 md / git tag 不一致 | 构建脚本的版本常量随手改；发布前跑 `verify_repo.py` | Railways 元数据曾停留 v1.0 |
| 把分析报告的致谢套到规则书 | 规则书用"术语与疑难条款参考了 18xx.games 社区…"；不写"全部对局数据来自…" | 语义不成立，2026-10-25 修正 |

## 典型使用场景

### 场景一：新系列规则翻译
> 用户：“我需要你按照规则的一般惯用格式（分两栏、基于原文本逐字翻译、专业名词），对 SCS IC（铁幕）的规则进行翻译，生成.md文件”

→ 执行完整流程：抽取核对 → 术语库 → 逐字翻译 → 对照检查 → 可信度评估 → 输出

### 场景二：多系列批量翻译
> 用户：“TCS系列的专规GD42需要翻译。先建立TCS专业名词对照库（通规+已有中文规则），再逐字翻译专规。”

→ 重点：先确认系列 → 定位通规和已有中文规则 → 建该系列的对照库 → 翻译专规

### 场景三：翻译质量修正
> 用户：“你没有如实翻译原文，频繁出现缩写、现编、不对应翻译的问题...修改你原来那个.md文件”

→ 这意味着需要**全文重译**而非修正个别地方。从第一步开始重做，逐句对照原文检查。

### 场景四：含扩展内容的翻译
> 用户：“TME分为东西两线作战，规则不一。翻译TMEE_Rules_2015和TMEE_Expansion_2015”

→ 先处理基础规则，再处理扩展规则。注意扩展规则可能修改/覆盖基础规则，翻译时保持一致；合订本用排版 skill 的部分横幅/侧边色签。

### 场景五：翻译 + 排版两步交付
> 用户：“把 GBII 重印版规则翻译成中文，并排成 PDF。”

→ 先按本 skill 出 `.md`（术语依据 OCS 4.3/2.0i/朝鲜战争/第三个冬天中译），再按 `wargame-rulebook-layout` 出 Ds 版 PDF；插图先普查后嵌入，交付时给 N/N 核验。

### 场景六：原书勘误密集的作品
> 用户：“这本 VUCA 规则书目录页码好像不对，规则和示例也打架。”

→ 按第一步 1.2 建勘误注记；正文照译；规则/示例矛盾单独标红提醒；评估里说明影响范围。

## 翻译标准速查

| 原则 | 说明 |
|:-----|:-----|
| **逐字逐句** | 每个英文句子 → 一个中文句子 |
| **不缩写** | 原文所有内容全部翻译 |
| **不扩写** | 不加原文没有的解释 |
| **不杜撰** | 术语查对照库，不在库中的先标记 |
| **编号一致** | 标题编号与原文完全相同 |
| **术语统一** | 同一个英文词全文档使用同一中文译法 |
| **逻辑保持** | 不为了可读性改变因果关系 |
| **系列独立** | 不同系列的术语库独立，不混用 |
| **错误留底** | 原书错误照译，另设勘误注记 |
| **可评可信** | 每本附四维可信度评估 |
